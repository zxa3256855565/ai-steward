## 为什么需要它

真实教训（已泛化）：

- 某脚本十天前被创建、**零记录**——排查时只能靠文件时间戳 + 逆向读源码猜测用途，花掉的 token 足够当初写一百行登记；
- 某次清理只删了脚本文件、**没杀它拉起的进程**——端口被占、服务起不来，故障排查绕了一大圈。

结论：**没有登记的环境，问题永远查不到根。** 而登记要趁早——脚本落地的那一条回复里就要写完。

## 两条铁律

### 铁律一：脚本登记（六要素）

任何对话在管辖环境**创建 / 修改 / 删除**的脚本类资产（.sh / .py / cron 条目 / systemd 单元 / compose 片段 / 调度器任务等），**当场**写入手册 + Agent 记忆，缺一不可：

| # | 要素 | 说明 |
|---|------|------|
| 1 | 路径 | 文件或条目的确切位置 |
| 2 | 作用 | 一两句话说清它干什么 |
| 3 | 影响模块 | 它坏了会连累谁 |
| 4 | 触发方式 | cron / 面板钩子 / 手动 / 随容器 |
| 5 | 日期 | 创建或修改时间 |
| 6 | **来源归属** | **哪个 Agent 的哪个对话**（Agent 名 + Session ID + 任务背景） |

> 删除脚本同样要登记，并记录**是否连带杀进程 / 摘 cron**——「删文件不杀进程」是真实发生过的事故。

### 铁律二：三注册面意识

**文件存在 ≠ 在运行。** 持续影响只来自注册面，排查顺序固定为：

1. cron / crontab -l
2. systemd 单元 / init.d
3. 系统自启（自启动目录、注册表 Run 键）
4. 调度器类（如 DSH schedule_list、Windows 任务计划）

四个注册面都干净，残留文件才只是「查档不便」，不是「在作恶」。

## 三册手册结构

按域分册、互为姊妹，每册头部固定放置铁律指引进度条：

    维护手册/
    ├── <主机A>维护手册.md      # 网络设备 / 服务器域
    ├── <主机B>维护手册.md      # 本机 / 工作站域
    └── <平台>维护手册.md       # 平台 / 插件 / 工具链域

- **新条目在上**（倒序时间线），每条含完整要素与「另见」交叉引用
- 排障结论、误判纠正、回滚点全部入册——**误判比成功更值得记**
- 模板见 [templates/](templates/)

## 排查方法论

环境出问题「清理了还是不对」时，固定三步：

1. **grep 脚本名** → 三本手册 + 记忆库 → 直接拿到「作用 + 影响模块 + 来源会话」
2. **查三注册面** → 确认它是否真的在运行
3. **都对不上** → 就是新的漏网 → 按铁律当场补录（事后补录要标注）

## 接入你的 Agent

把 [rules/](rules/) 下的铁律文本作为系统指令 / Skill / 自定义指令贴入你的 Agent（Claude Code、DeepSeek Harness、Codex、ChatGPT 均可），并在首次对话中告诉它你的管辖环境清单（几台机器、几个平台）。**从下一个脚本开始执行，比从明天开始执行更重要。**

## 灾备用法

本仓库同时是灾备预案：当本机数据受损，clone 本仓库即可找回整套管家体系（铁律 + 手册结构 + 模板），按「接入你的 Agent」一节重新铺开。
